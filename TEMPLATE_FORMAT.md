# Файлы шаблонов

Исходники опубликованных историй хранятся обычными файлами в этом репозитории:

```text
public/templates/
  index.json
  <story-id>/r<revision>/
    manifest.json
    modules/
      prompt-<id>.md
      setting-<id>.md
      player-<id>.md
      lead-<id>.md
      support-<id>.md
      opening-<id>.md
    images/<module-id>.jpg
```

`support` может отсутствовать или повторяться. Остальные роли — ровно по одному
модулю. `player` — персонаж под контролем игрока, `lead` — второй главный герой
(не обязательно романтический интерес). Картинки необязательны у сеттинга и всех
персонажей. ZIP не является форматом хранения: бот упаковывает файлы только для
удобного скачивания из Telegram.

`manifest.json`: `format: "simpledeepseek.story"`, `version: 1`, постоянный `id`,
`title`, целочисленная `revision`, массив `modules`. У каждого модуля — постоянный
`id`, `kind`, `title`, относительный путь `file`, `file_sha256`, `complete: true`.
При наличии картинки: `image`, `image_sha256`, `image_width`, `image_height`;
иначе `image: null`. ID не содержит Telegram ID. Переписки редактора нет в шаблоне.

Текст — UTF-8 Markdown, до 12000 символов на модуль и 60000 на сборку. Максимум
20 персонажей, включая альтер-эго и второго главного героя. Картинки — JPEG до
2 МиБ; бот нормализует загруженные JPEG/PNG/WebP и удаляет метаданные.

`templates/index.json` выбирает опубликованные версии и задаёт карточки:

```json
{
  "stories": [{
    "manifest": "templates/STORY_ID/r5/manifest.json",
    "summary": "Короткая аннотация",
    "author": {"name": "Псевдоним"},
    "categories": ["Приключение"],
    "tags": []
  }]
}
```

`npm run build` проверяет роли, размеры, ссылки и SHA-256, затем генерирует
`public/catalog.json` для интерфейса. Этот файл — производный индекс, его тексты
не редактируют вручную. Карточка содержит ссылку и хеш manifest. При выборе
готовой истории бот загружает manifest, Markdown и картинки только с адреса
своего каталога, проверяет хеши и сохраняет собственную копию всей версии.
Изменение репозитория не меняет уже начатую игру.

`.gitattributes` сохраняет байты файлов шаблонов без преобразования переносов
строк Git на Windows: это необходимо для совпадения SHA-256 после публикации.

## Подготовка публикации администратором

1. Автор создаёт черновик через `/builder`, проверяет и сохраняет каждый модуль,
   пробует личную игру. Номер сборки показан в мастерской.
2. Администратор согласует публикацию конкретных текстов и картинок с автором.
3. Из корня репозитория бота выполнить:

   ```powershell
   .venv/Scripts/python.exe -m botapp.builder_export --build 123 --catalog catalog
   ```

   Команда читает БД в режиме read-only, копирует только сохранённые модули и
   выбранные картинки, добавляет версию в индекс. Неполные сборки и неподтверждённые
   предложения не принимаются. Существующую версию с другими байтами не затирает.
   Команда не коммитит и не пушит. Не копируй сюда весь `data/`.
4. Заполнить аннотацию и псевдоним в `templates/index.json`, проверить все файлы,
   выполнить `npm test` и `npm run build`, затем коммит/пуш в репозитории каталога.
5. Публикация завершена после успешного GitHub Pages deployment.

Новые редакции получают новую папку `rN`; индекс переключается на неё. Для
изменённого Markdown обновляют его SHA-256 в manifest. Надёжнее редактировать
сборку через Telegram и экспортировать новую ревизию. Старые версии можно хранить
для истории изменений; снятие карточки не удаляет файлы из Git-истории.

Авторские заявки и очередь модерации работают в Telegram: `/builder` →
«Отправить в каталог», очередь супер-админа — `/moderation`. Одобрение запускает
экспорт именно проверенного снимка в служебном checkout, сборку и push. Ссылка
отправляется после подтверждения Pages и публичных файлов. Процесс: [UGC](UGC.md).
Веб-конструктор комбинаций пока использует прежние
описания модулей из индекса; полный пакет с исходным промптом и файлами копируется
по кнопке «Играть» у готовой истории.
